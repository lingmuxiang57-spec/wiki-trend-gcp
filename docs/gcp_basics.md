# 1. プロジェクト・リージョン・課金
- プロジェクトとは何か。ID・表示名・番号の違い
    - **プロジェクト**：Cloud Run・バケット・データセットなどのリソースを入れる「入れ物」。権限や料金も、プロジェクト単位で管理する
    - **ID**：自分で決める、後から変更できない識別子（例：`pantarhei-wiki-trend-20261116`）。コマンドの `--project` にはこれを使う
    - **表示名**：画面に出る名前。後から変更できる（例：`Panta Rhei Wiki Trend`）
    - **番号**：Google が自動で振る数字（例：`32614732480`）。Cloud Run の URL などに出てくる
    - Phase 0 で、`--project` に表示名を入れてエラーになった。迷ったら `gcloud projects list` で ID を確認する
- リソース階層
    - 組織 → フォルダ → プロジェクト → リソース（Cloud Run・バケットなど）の順に、入れ子になっている
    - 上の階層で付けた IAM の権限は、下の階層に引き継がれる
    - **自分の構成では**：個人の Gmail で作ったので、組織やフォルダはなく、プロジェクトが一番上
- リージョンとゾーンの違い
    - **リージョン**：データセンター群がある地理的な場所（例：`asia-northeast1` = 東京）
    - **ゾーン**：リージョン内の独立した区画（例：`asia-northeast1-a`）。
  電源やネットワークが分かれているので、1つのゾーンに障害が起きても他のゾーンは動き続ける。
  - **自分の構成では**：Cloud Run・GCS・BigQuery・Artifact Registry をすべて`asia-northeast1` に揃える。
    - 理由1：BigQuery は別ロケーションの GCS からロードするとエラーになる
    - 理由2：リージョン間のデータ転送料金がかからない
    - 理由3：日本から使うのでレイテンシが小さい
- Cloud Run はリージョン単位のサービスなので、ゾーンを意識しなくてよい
  （ゾーン間の冗長化を Google 側がやってくれる）
- 参考：https://cloud.google.com/about/locations
- 課金アカウント・プロジェクト・Googleアカウントの関係
    - **Google アカウント**（メールアドレス）：操作する「人」
    - **課金アカウント**：「支払い方法」（クレジットカードなど）。ID は `XXXXXX-XXXXXX-XXXXXX` の形
    - **プロジェクト**：「リソースの入れ物」
    - プロジェクトを課金アカウントに紐付けると、そのプロジェクトの料金がその支払い方法に請求される。1つの課金アカウントに、複数のプロジェクトを紐付けられる
    - Phase 0 で、`--billing-account` にメールアドレスを入れてエラーになった。人（メールアドレス）と支払い方法（課金アカウント ID）は別物
- 無料枠（今回の構成で関係するもの）
    - **Cloud Run**：毎月、一定のリクエスト数と、CPU・メモリの使用時間まで無料。API はアクセスが少なく、batch は1日1回数十秒なので、ほぼ無料枠に収まる
    - **BigQuery**：毎月 1 TB のクエリと 10 GB のストレージまで無料。今回のデータは 1 MB 未満なので、十分に収まる
    - **Cloud Scheduler**：3ジョブまで無料。今回は1ジョブ
- 予算アラート
    - 月 1,000 円の予算で、50%・90%・100% で通知するように設定した
    - 予算アラートは**通知するだけで、使用を止めない**。予算を超えても課金は続くので、通知を見たら自分で原因を調べて止める必要がある

# 2. IAMと最小権限
- プリンシパル、ロール、ポリシー
    - **プリンシパル**：「誰が」。ユーザー（Google アカウント）やサービスアカウント（SA）など
    - **ロール**：「何をしてよいか」。権限のまとまり（例：`roles/bigquery.dataViewer` は、データを読む権限のまとまり）
    - **ポリシー**：「どのリソースで、誰に、どのロールを付けるか」の対応表。プロジェクト・バケット・データセット・Job など、リソースごとにポリシーがある
- なぜ、OwnerやEditorの付与を避けるのか
    - Owner や Editor は、プロジェクトの中のほぼすべてを操作できる
    - その SA が乗っ取られたり、コードにバグがあったりしたときに、関係ないリソースまで消されたり、書き換えられたりする危険がある
    - 必要な権限だけを付けておけば、被害をその範囲に抑えられる（**最小権限の原則**）
- 権限を付与する場所
    - できるだけ**狭い範囲**に付けた
        - batch の SA の GCS 権限：バケット単位
        - BigQuery のデータの権限：データセット単位
        - Scheduler の SA の起動権限：Job 単位
        - Cloud Build の SA の push 権限：Artifact Registry のリポジトリ単位
    - ただし、`roles/bigquery.jobUser` は、ジョブがプロジェクト単位のものなので、プロジェクトに付けた
- サービスアカウントを用途ごとに分けた理由
    - 今回は `wiki-batch`（データ取得）・`wiki-scheduler`（Job の起動）・`wiki-api`（API）・`wiki-cloudbuild`（自動デプロイ）の4つに分けた
    - 役割ごとに必要な権限が違うから。API は読むだけなので `dataViewer`、batch は書き込むので `dataEditor`
    - 1つの SA にまとめると、その SA はすべての権限を合わせ持つことになる。そうすると、API が乗っ取られたときに、データを書き換えられてしまう
- サービスアカウントと鍵を作らない理由。ADCとCloud Runに紐付けたサービスアカウントによる認証
    - 鍵ファイル（JSON）は、漏れると誰でもその SA になりすませる。GitHub に誤って push する危険もある
    - 代わりに、次の方法で認証した。同じコードのまま、鍵なしで動く
        - **ローカル**：ADC（`gcloud auth application-default login` で、自分のアカウントの認証情報を使う）
        - **Cloud Run（Service / Jobs）**：紐付けた SA の認証情報が、自動で使われる
- 今回の経験で実感したこと
    - 権限が足りないときは `403` や `PERMISSION_DENIED` になり、エラー文に「足りない権限名」と「対象」が書いてある。Phase 3 では `Permission bigquery.tables.create denied on dataset ...` から、データセットに `dataEditor` が足りないと分かった

# 3. IaaS/ Paas / サーバーレス
- 誰が何を管理するかで比べる
    - **IaaS**：仮想マシン（サーバー）を借りる。OS の更新・ミドルウェア・アプリ・台数の調整は、すべて自分で行う
    - **PaaS**：アプリのコードを渡せば、OS や実行環境は事業者が管理する
    - **サーバーレス**：サーバーを意識しない。リクエストや処理があったときだけ動き、台数の調整（0台を含む）も自動。使った分だけ課金される
- GCPの代表例
    - IaaS：Compute Engine
    - PaaS：App Engine
    - サーバーレス：Cloud Run・Cloud Functions・BigQuery（BigQuery もサーバーを用意せず、クエリで読んだ量だけ課金される）
- Cloud Runの位置付け：コンテナを持ち込めるサーバーレス。
    - Dockerfile で実行環境（Python のバージョンやライブラリ）を自分で決められるので、PaaS より自由。それでいて、サーバーの管理や台数の調整はしなくてよいので、IaaS より楽
    - **自分の構成では**：同じ Docker イメージの仕組みで、HTTP の API（Cloud Run Service：`wiki-api`）と、1回動いて終わるデータ取得の処理（Cloud Run Jobs：`wiki-batch`）の両方を動かせた
